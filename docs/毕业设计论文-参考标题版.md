## 摘　要

在**教育信息化**与**智慧校园**持续推进的背景下，**教室、实验室、报告厅**等场地资源的分配若仍依赖纸质登记、群内接龙或多套表格，容易出现**时段重叠、责任不清、事后难以统计**等问题；师生希望能在统一入口查询「某时段是否仍可预约」，管理人员则希望审批与名单能够留痕、可对账。传统**单体 Web** 将多业务模块置于同一进程，在开发早期交付快，但随着模块堆叠与用户并发上升，往往面临**发版粒度粗、扩容只能整体复制、故障影响面大**等局限。**微服务架构**强调按业务能力拆分服务、独立部署与轻量协议协作，有利于在可控复杂度下改善伸缩性与迭代效率[10][11]。

本文在 **Java 17** 与 **Spring Boot 3.3.7** 基线上，设计并实现了一套**基于 Spring Cloud 的教学资源预约系统**：后端划分为 **gateway-service、user-service、resource-service、booking-service** 四个可独立启动的 **Spring Boot** 应用，浏览器与前端构建产物仅访问 **Spring Cloud Gateway（9000）**，由网关将 **`/api/**`** 路由至 **9001～9003**，并在 **`globalcors`** 中集中处理**跨域（CORS）**，以降低业务服务重复配置、响应头叠加导致前端 **`Failed to fetch`** 而 **HTTP 状态码却可能仍为 200** 的排错难度；**resource-service** 在计算某时段**可用资源**时，通过 **OpenFeign** 调用 **booking-service** 暴露的内部 **`GET /internal/bookings/conflicting-resource-ids`**，取得**冲突资源 ID 集合**后在服务内存中过滤，使「是否已被占用」的判定集中在预约权威侧；持久化采用 **MySQL** 与 **MyBatis-Plus**，预约提交链引入 **Redis** 与 **Redisson**，以 **`tryLock`** 等语义缓解同一时刻多人提交造成的写库竞争；前端采用 **Vue 3 + Vite + Ant Design Vue**，通过 **`VITE_API_BASE`** 将 **API** 根指向网关，便于在不同部署环境切换主机名。工程内保留 **demospringboot（8080）** 单体实现与 **platform** 微服务实现，便于在相同 **MySQL** 数据条件下开展**对照实验**与论文中的架构对比叙述。

论文按照**绪论—开发环境与相关技术—系统需求分析—系统概要设计—系统详细设计与实现—系统测试—总结与展望**组织；主要创新点体现在：**一是**落实了「网关统一外网入口 + **booking-service** 为预约权威 + **Feign** 拉冲突 **ID** + **resource-service** 侧过滤」的协作链，避免占用逻辑在多个服务中各写一套；**二是**将 **Redisson** 分布式锁嵌入真实预约提交路径，并与单体版本在同一数据集上作耗时与失败现象对照。架构图、时序图、**API** 列表、黑盒测试用例与实验记录模板见 **`docs/thesis/`** 及 **`docs/thesis/diagrams/`**，定稿时须按学校规范插入正文并编号。**参考文献**表共列 **42** 篇。

## Abstract

Under digital-campus and informatization initiatives, **classrooms, laboratories, and lecture halls** need transparent online booking; legacy workflows cause **slot conflicts and weak accountability**, while **monolithic Web** stacks release and scale coarsely as modules grow. **Microservices** improve modularity and isolation[10][11].

This thesis implements a **Spring Boot 3.3.7** teaching-resource reservation system on **Java 17** with **gateway-service**, **user-service**, **resource-service**, and **booking-service**. **Spring Cloud Gateway (9000)** routes **`/api/**`** to **9001–9003** and centralizes **CORS** to avoid duplicated headers and misleading **`Failed to fetch`** errors. **resource-service** calls **`/internal/bookings/conflicting-resource-ids`** on **booking-service** via **OpenFeign** to fetch **conflicting resource IDs** before filtering. **MySQL** and **MyBatis-Plus** persist data; **Redis** and **Redisson** guard the booking path with **`tryLock`**. The UI uses **Vue 3**, **Vite**, and **Ant Design Vue** with **`VITE_API_BASE`** at the gateway. The **demospringboot** monolith (**8080**) is retained for comparison on the same dataset.

The thesis follows the standard seven-chapter layout; diagrams and templates live under **`docs/thesis/`**. The reference list contains **42** entries.

**Keywords**: teaching-resource reservation; Spring Cloud Gateway; microservices; OpenFeign; Redis; Redisson; Vue 3

## 第 1 章　绪论

### 1.1 研究背景（Research Background）

高校在日常教学、集中实验与考务活动中，对**教室、实验室、报告厅**等场地类资源的需求具有**时段集中、峰谷明显**的特点；若仍依赖纸质申请、电话协调或各学院分散维护的电子表格，信息往往难以同步，**重复预约、临时插队、责任追溯困难**等问题会反复消耗管理人员精力。将预约、查询与审批迁移到统一的信息系统，一方面可以让师生在任意可联网终端上自助完成操作，另一方面可以把「谁在什么时段占用了哪一间」以数据库记录的形式固定下来，为后续统计与审计提供基础。

从软件架构角度看，许多早期系统采用**单体 Spring Boot** 将所有模块置于同一进程：在团队规模较小、功能迭代较慢时，这种方式**开发路径短、调试方便**；当用户量与接口数量上升后，常见矛盾包括**单次发布影响面大、无法仅对热点模块水平扩容、代码库膨胀导致新人上手成本上升**等。**微服务架构**倡导将系统拆分为围绕业务能力构建、可独立部署的小服务，通过 **HTTP REST** 等轻量协议协作，在**伸缩粒度、故障隔离与多团队并行开发**上更具弹性[10][11]。在 **Java** 生态中，**Spring Cloud Gateway** 适合承担统一入口与横切能力，**OpenFeign** 适合以接口契约方式组织服务间调用[1][2][3]，与本科毕设周期内的可落地性相匹配。

本课题在**可维护性、可扩展性与可验证性**目标下，实现**基于 Spring Cloud 的教学资源预约系统**；工程上同时保留 **demospringboot（8080）** 单体版本与 **platform（经 Gateway 9000 接入）** 微服务版本，使论文既能阐述拆分理由，也能在相同 **MySQL** 数据条件下记录**对照实验**现象，避免停留在概念层面。

### 1.2 研究现状（Research Status）

**国外**在高校与公共机构的场地预约、日历与身份系统集成等方面起步较早；工业界围绕**微服务拆分、API 网关、服务网格与可观测性**已形成大量实践与模式总结[10][11]。**Spring** 官方对 **Spring Boot 3、Spring Cloud Gateway、OpenFeign** 等组件持续维护文档与示例，降低了在 **Java** 技术栈上复现「网关 + 多服务」路径的成本[1][2][3]。**API** 统一入口与治理亦与 **OWASP** 等组织对 **API** 安全的讨论相呼应[14]。

**国内**高校信息化建设普遍覆盖**教务、一卡通、实验室管理**等业务域，其中不少子系统带有预约或借用能力；在 **CNKI、万方** 等数据库中，以「智慧校园、实验室开放、资源预约、并发控制」等为关键词可检索到较多期刊与学位论文，说明该方向具有持续研究价值。工程实现上，**前后端分离 + 网关收拢入口 + Redis 做缓存或锁**的组合在近几年项目中十分常见。与泛泛的技术选型文章相比，本文工作侧重于把**预约权威与冲突判定**明确落在 **booking-service**，通过 **Feign** 向 **resource-service** 提供**冲突资源 ID**，并在预约提交路径上引入 **Redisson**，使设计决策与 **`platform`** 仓库中的类、配置与端口划分一一对应；定稿前尚须在数据库中**检索、阅读原文**后，将参考文献表中的中文占位条目替换为真实著录。

## 第 2 章　开发环境和相关技术

### 2.1 开发环境（Development Environment）

本系统采用**前后端分离 + 微服务**分层，各层工具链与版本以仓库 **`platform/pom.xml`**、**`demovue3/package.json`** 及实际 **`application.yml`** 为准，开发环境可概括如下。

（1）**前端（Web 端）**：以 **JavaScript** 与 **Vue 3** 单文件组件为主，**Vite** 作为开发与构建工具，**Ant Design Vue** 提供表单、表格与布局等组件；工程目录 **`demovue3`**，常用命令为 **`npm install`**（安装依赖）、**`npm run dev`**（启动开发服务器，默认本地端口以 **Vite** 控制台为准）、**`npm run build`**（产出 **`dist`** 静态资源）。接口根地址通过环境变量 **`VITE_API_BASE`** 指向 **Spring Cloud Gateway**，避免在源码中硬编码 **9000** 或线上域名。建议 **Node.js 18 LTS 及以上**；本仓库 **`package.json`** 中 **Vue** 为 **^3.5.13**、**Vite** 为 **^6.0.3**、**ant-design-vue** 为 **^4.2.6**。浏览器可选用 **Chrome** 或 **Edge**；编辑器可选用 **Visual Studio Code**（配合 **Vue** 插件）或 **IntelliJ IDEA**。

（2）**HTTP 服务端（网关与业务微服务）**：**JDK 17**；**Spring Boot 3.3.7**（父 **POM** **`spring-boot-starter-parent`**）；**Spring Cloud 2023.0.4**（属性 **`spring-cloud.version`**）；构建工具 **Apache Maven 3.8+**；多模块父工程 **`platform`**，子模块包括 **gateway-service、user-service、resource-service、booking-service** 与 **common-lib**。对外协议为 **HTTP**，请求与响应体普遍采用 **JSON** 序列化。各服务默认监听端口：**Gateway 9000**，**user-service 9001**，**resource-service 9002**，**booking-service 9003**（若本地修改 **`server.port`** 以联调为准）。

（3）**微服务间内部调用**：**resource-service** 通过 **OpenFeign** 声明式客户端访问 **booking-service** 的内部 **REST**（如 **`/internal/bookings/conflicting-resource-ids`**），默认 **`booking.service.url=http://127.0.0.1:9003`**，**不经 Gateway**，与浏览器流量分离，降低将内部接口误暴露到公网路由的风险。

（4）**数据库、中间件与文档环境**：业务数据使用 **MySQL 8.x**；预约并发控制使用 **Redis**，客户端可选用 **MySQL Workbench**、**DBeaver**、**`mysql`**、**`redis-cli`** 等。论文配套 **API** 说明、黑盒测试用例、实验记录表、部署示例及 **Mermaid** 图源位于 **`docs/thesis/`** 与 **`docs/thesis/diagrams/`**。与微服务对照的**单体**工程为 **`demospringboot`**（**Spring Boot 3.3.7**，默认 **8080**），数据库可与 **platform** 共用 **`wwq_bs`** 一套表，便于对照实验。

### 2.2 微服务架构（Microservice Architecture）

#### 2.2.1 单体架构模式

**单体架构**将表现层、业务层与数据访问层打包在同一可执行单元（如单个 **Spring Boot jar**）中，模块间以**进程内方法调用**为主，部署与调试路径简单，适合功能较少、团队较小的阶段。其局限在于：随着代码规模增长，**编译与启动时间变长**；任何一处缺陷修复往往牵动**整包发版**；流量上升时通常只能**整体水平扩展**副本，难以仅对「预约」或「资源查询」等热点单独加实例[10][11]。本仓库 **`demospringboot`** 在 **8080** 端口提供与微服务版本相近的业务能力，用于论文中的对照叙述与实验基线。

#### 2.2.2 微服务架构模式

**微服务架构**将系统拆为一组**松耦合、可独立部署**的服务，每个服务围绕具体业务能力构建，拥有相对清晰的代码库与发布节奏，服务之间通过 **HTTP REST** 等协议通信[10][11]。其常见工程收益包括：（1）**可扩展性**——可对高负载服务单独扩容；（2）**迭代效率**——各服务可并行演进、独立发版；（3）**故障隔离**——异常多局限于单个服务实例；（4）**可理解性**——仓库与包边界与业务名词更易对齐。代价则包括：**分布式事务与数据一致性**需额外设计；**联调与集成测试**依赖稳定的路由与配置；**观测与排障**需要日志规范与健康检查等支撑。本课题 **platform** 将**用户、资源、预约**拆为三个业务 **jar**，并由 **Gateway** 承担外网入口与 **CORS**；未引入的 **Nacos、Sentinel** 等留待第 7 章展望，以控制毕设工作量。

### 2.3 Spring Boot 与 Spring Cloud 简介（Spring Boot and Spring Cloud）

**Spring Boot** 通过起步依赖与自动配置显著减少 **XML** 与样板代码，内嵌 **Servlet** 容器，适合快速构建可运行的 **Web** 与 **REST** 服务[1]。**Spring Boot 3** 以 **Java 17** 为最低版本，全面迁移至 **Jakarta EE** 包名，并与 **Spring Framework 6** 对齐，在依赖管理与观测钩子等方面较 **2.x** 线更为一致；官方亦提供 **AOT**、**Native Image** 相关指引，便于后续向容器镜像与短启动路径演进。

**Spring Cloud** 在 **Boot** 之上提供与分布式系统常见横切关注点相关的组件族。本课题选用 **Spring Cloud 2023.0.x** 与 **Boot 3.3.x** 的 **BOM** 对齐，减少版本冲突。**Spring Cloud Gateway** 基于 **Project Reactor** 与 **Netty**，通过 **`Route`（路由规则）、`Predicate`（匹配条件）、`Filter`（过滤器链）** 将入站请求转发到下游 **`URI`**[2]；本课题在网关中配置 **`spring.cloud.gateway.routes`** 将 **`/api/login`** 等路径分发至 **user-service**，将 **`/api/resource`** 等分发至 **resource-service**，将 **`/api/booking/**`、`/api/approval/**`** 分发至 **booking-service**，并在 **`globalcors`** 中声明允许的源与方法。需强调：**若业务服务仍启用 `WebMvc` 级 CORS**，可能与网关响应头叠加，浏览器端表现为 **`Failed to fetch`**，排错时应优先比对 **`Access-Control-Allow-Origin`** 是否重复。

**OpenFeign** 以 **`@FeignClient` 接口**声明远程 **HTTP**，运行时生成代理完成编解码与错误包装[3]；本课题 **resource-service** 通过 **Feign** 调用 **booking-service** 内部冲突查询接口，实现「资源视图」与「预约事实」的解耦。

### 2.4 MySQL 与 MyBatis-Plus 简介（MySQL and MyBatis-Plus）

**MySQL** 是成熟的开源关系型数据库，支持 **InnoDB** 事务引擎、主从复制与常见 **SQL** 分析能力[6]，足以承载本课题用户、资源与预约等结构化数据。设计时通过主键、外键语义（或在应用层保证参照完整性）维护 **`sys_booking`** 与 **`sys_resource`、`auth_user`** 之间的关联；在高并发写入场景下，仍需结合业务锁与合理索引控制锁竞争范围。

**MyBatis-Plus** 在 **MyBatis** 的 **SQL** 映射能力之上，提供 **`LambdaQueryWrapper`**、通用 **Mapper**、分页插件等[8]，使列名以 **Lambda** 方式引用，减少手写 **XML** 时的拼写错误；本课题各服务的 **Entity** 与 **`Mapper`** 接口与 **`auth_user`、`sys_resource`、`sys_booking`** 等表一一对应。

**Redis** 提供内存级键值存储与键过期能力[7]，适合实现短 TTL 的互斥或缓存；**Redisson** 在 **Java** 侧封装 **`RLock`、`tryLock`、leaseTime、watchdog`** 等分布式锁语义[5]，本课题在 **booking-service** 的预约提交实现中，在写入 **`sys_booking`** 前获取锁，失败时向调用方返回可理解的业务提示，与数据库事务配合形成「先争用、再落库」的秩序。

### 2.5 本章小结（Chapter Summary）

本章说明了本课题的前后端与中间件开发环境，从单体与微服务两方面归纳了架构取舍，阐述了 **Spring Boot 3、Spring Cloud Gateway、OpenFeign** 在本系统中的职责边界，并介绍了 **MySQL、MyBatis-Plus、Redis、Redisson** 在持久化与并发控制中的作用，为第 3～5 章的需求、设计与实现提供统一术语基础。

## 第 3 章　系统需求分析

### 3.1 可行性分析（Feasibility Analysis）

**经济可行性**：后端与前端主体采用 **Spring Boot、Spring Cloud、Vue、MySQL、Redis** 等开源技术栈，无需采购商业应用服务器即可在实验室 **PC** 或低配云主机上完成开发与演示；人力成本主要为需求理解、联调与论文撰写时间。若系统能在真实场景中减少人工协调与重复登记，其长期收益可覆盖一次性建设成本。

**技术可行性**：**Java** 与 **Spring** 官方及社区文档齐全[1][12]；**Vue 3** 与 **Vite** 的前端资料完备[4]；微服务拆分、网关路由、声明式 **HTTP** 客户端与 **Redis** 锁等模式在公开书籍与案例库中均有成熟讨论[10][11]；本仓库 **`platform`** 已实现可运行微服务版本，并与 **`demospringboot`** 共用或兼容同一套库表设计，说明所选技术路线在毕设周期内可落地。

**操作可行性**：师生侧仅需浏览器即可完成注册、登录、查询可用资源、提交预约与查看个人记录；管理员在同一套前端中完成用户维护、资源启停与审批。部署阶段可采用 **Nginx** 托管 **`dist`** 并将 **`/api/`** 反向代理至 **127.0.0.1:9000**，用户侧只需记住站点域名，学习成本相对可控。

### 3.2 功能性需求分析（Functional Requirements Analysis）

系统功能按业务域划分如下，对应 **`platform`** 中的服务边界。

（1）**用户与认证（user-service）**：普通用户完成**注册、登录、修改密码**；管理员在 **`/api/admin/user/**`** 路径下完成用户**列表查询、新增、删除、模板下载与 Excel 导入导出**等维护操作；登录成功后返回角色信息，供前端路由与按钮级权限控制使用。

（2）**资源管理（resource-service）**：管理员对 **`sys_resource`** 执行**新增、修改、删除、启用、停用**；师生在前台按**日期与时段**查询**当前仍可选的资源列表**；该列表必须在服务端剔除与已有预约**时间窗重叠**的资源，剔除逻辑依赖第（4）条跨服务调用。

（3）**预约与审批（booking-service）**：用户提交预约、查看「我的预约」、在规则允许下**取消**；管理员或审批角色在审批列表中对记录执行**通过或驳回**；预约事实以 **`sys_booking`** 为权威存储。

（4）**跨服务可用资源查询**：**resource-service** 在组装前台查询结果时，须调用 **booking-service** 内部接口 **`GET /internal/bookings/conflicting-resource-ids`**，传入 **`date、startTime、endTime`**（**ISO-8601** 字符串），获得冲突资源 **ID** 集合后在内存中过滤；**禁止**在 **resource-service** 侧用简化规则「猜测」占用情况，以免与预约库不一致。

### 3.3 非功能性需求分析（Non-Functional Requirements Analysis）

**性能**：在选课或集中实验等高峰场景下，系统应能处理一定并发查询与预约提交；对同一资源的并发提交应通过**分布式锁或数据库约束**避免写乱，并对失败请求给出明确提示而非 **500** 泛化错误。**可用性**：各服务应输出结构化日志，并可通过 **Spring Boot Actuator** 的 **`/actuator/health`** 等端点做存活探测。**安全**：生产环境数据库口令、**Redis** 口令等不得写入公开版本库；**`/internal/**`** 仅允许内网访问，不得出现在 **Gateway** 对外路由表中。**可维护性**：前后端分离、服务边界清晰后，需求变更（如审批流调整）应能定位到具体 **jar** 与前端模块，降低回归成本。

### 3.4 本章小结（Chapter Summary）

本章从可行性、功能与非功能三个维度界定了本系统的建设目标与范围，明确了 **user、resource、booking** 三服务的职责及 **Feign** 内部协作在功能需求中的必要性，为概要设计与详细设计提供依据。

## 第 4 章　系统概要设计

### 4.1 总体架构设计（Overall System Architecture Design）

从**逻辑分层**角度，系统自顶向下可分为：**表现层**（浏览器中的 **Vue SPA**）、**接入层**（**Spring Cloud Gateway**）、**业务服务层**（**user-service、resource-service、booking-service** 三个 **Spring Boot** 应用）、**数据层**（**MySQL**）以及**中间件层**（**Redis**，主要服务于预约链路的互斥）。用户请求自浏览器发出后，仅与 **Gateway** 建立连接，由网关根据路径前缀将流量转发至对应下游服务；**OpenFeign** 调用则发生在业务服务进程之间，不经过浏览器，从而形成「**外网入口单一、内网协作清晰**」的拓扑。

从**物理部署**角度，本科毕设阶段可将 **Gateway、三个业务服务、MySQL、Redis** 部署于同一台主机，通过 **`127.0.0.1`** 互通即可满足联调；若需对外演示，可在该主机上再增加 **Nginx** 托管前端 **`dist`** 并反向代理 **`/api/`** 至 **9000**。系统架构示意图源文件建议使用 **`docs/thesis/diagrams/01-system-architecture.md`** 导出后插入正文。

### 4.2 软件架构设计（Software Architecture Design）

**端口与职责划分**：**9000** 由 **gateway-service** 占用，统一接收 **`/api/**`** 并配置 **`globalcors`**；**9001** 由 **user-service** 承担**认证与用户管理**；**9002** 由 **resource-service** 承担**资源维护及前台资源查询（含 Feign 聚合）**；**9003** 由 **booking-service** 承担**预约、审批、内部冲突查询**及 **Redis/Redisson** 相关逻辑。前端 **`VITE_API_BASE`** 仅指向 **`http(s)://<网关或 Nginx 域名>`**，避免前端直接依赖 **9001～9003**，为后续在网关层统一接入 **JWT**、限流等横切能力创造条件。

**路由原则（摘要）**：**`/api/login`、`/api/register`、`/api/changePassword`** 与 **`/api/admin/user/**`** 转发至 **user-service**；**`/api/resource`** 与 **`/api/admin/list|add|disable|enable`** 转发至 **resource-service**；**`/api/booking/**`** 与 **`/api/approval/**`** 转发至 **booking-service**。完整路径、方法与请求体说明见 **`docs/thesis/API.md`**。需再次强调：**`/internal/...`** 不应出现在网关对外路由中，仅允许 **resource-service** 进程以内网地址访问。

### 4.3 数据库概要设计（Database Outline Design）

核心实体包括**用户、资源、预约**三类。**`auth_user`** 存储登录名、密码摘要、角色等；**`auth_student`、`auth_teacher`、`auth_manager`** 等扩展表存放不同角色附加属性（以实际库表为准）。**`sys_resource`** 描述场地或设备类资源及其启用状态。**`sys_booking`** 记录预约所关联的用户、资源、时段与审批状态，与 **`sys_resource`、`auth_user`** 在语义上构成多对一关联；辅助表如 **`booking_cleanup`** 可用于定时或批处理清理（若工程已启用）。**ER** 图建议使用 **`docs/thesis/diagrams/06-er-core-tables.md`** 导出。

### 4.4 本章小结（Chapter Summary）

本章给出了系统的逻辑分层与典型单机部署方式，明确了各服务端口、网关路由原则及核心表之间的概要关系，为第 5 章的接口级与类级详细设计提供蓝图。

## 第 5 章　系统详细设计与实现

### 5.1 数据库设计（Database Design）

在概要设计基础上，数据库实现需保证**字段类型、非空约束、默认值**与 **MyBatis-Plus** 实体类一致，避免映射失败。**`auth_user`** 承载登录凭证与角色枚举，是其它业务表关联用户的入口；密码字段应仅存**单向摘要**而非明文。**`sys_resource`** 除名称、容量等描述字段外，应包含**启用标志**，以便前台查询时快速过滤不可用资源。**`sys_booking`** 应能表达预约所对应的**资源 ID、用户 ID、日期与起止时刻、状态（待审/通过/驳回/取消）**；与 **`sys_resource`** 的关联保证「预约指向真实存在的资源」；时间字段建议统一为服务端可比较的格式，减少跨时区歧义。索引方面，对高频按用户、按资源、按日期查询的列组合可建立联合索引，以降低列表页与冲突扫描的开销；具体索引以实际 **`wwq_bs`** 库及迁移脚本为准。若表结构发生变更，需同步更新 **Mapper**、**Service** 与 **`docs/thesis/API.md`**。

### 5.2 用户模块（User Module）

**user-service** 对外暴露 **`AuthController`**（命名以仓库为准），聚合处理 **`POST /api/login`**、**`POST /api/register`**、**`POST /api/changePassword`** 等认证类接口：登录时按用户名查询 **`auth_user`**，校验密码摘要与角色字段，返回 **JSON** 供前端保存；注册时完成用户名唯一性检查与密码加密写入。管理员用户维护接口位于 **`/api/admin/user/**`** 路径下，实现分页列表、单条新增与删除、模板下载与 **Excel** 批量导入等能力；导入过程应在服务端做行级校验，对非法行返回可定位的错误信息。登录态在前端多以本地存储或会话存储维持（依 **`demovue3`** 现有实现），后续请求由浏览器自动携带 **Cookie** 或 **Header**（若未来引入 **JWT**，则可在网关统一校验 **Authorization**）。时序图可参考 **`docs/thesis/diagrams/03-sequence-login.md`**。

### 5.3 网关与路由模块（Gateway and Routing Module）

**gateway-service** 的配置集中在 **`application.yml`**：在 **`spring.cloud.gateway.routes`** 下为每一类 **`/api/**`** 前缀配置 **`id`、`uri`、`predicates`**；在 **`globalcors`** 中声明 **`allowedOrigins`/`allowedOriginPatterns`、`allowedMethods`、`allowedHeaders`** 等，使浏览器跨域预检 **`OPTIONS`** 与业务 **`GET/POST`** 均能正确返回。过滤器链后续可插入**鉴权、限流、请求日志**等自定义 **`GatewayFilter`**。工程上须遵守「**CORS 只在网关配一份**」的原则，避免业务 **`@CrossOrigin`** 与网关叠加；联调若出现 **`Access-Control-Allow-Origin`** 出现多个值，应优先检查各 **`application.yml`**。部署时 **Nginx** 可将 **`/api/`** 反代至 **`127.0.0.1:9000`**，实现 **HTTPS** 终止与静态资源分离。

### 5.4 资源管理模块（Resource Management Module）

**resource-service** 的 **`ResourceController`** 实现资源后台 **`/api/admin/...`** 与前台 **`/api/resource`** 查询。前台「可用资源」接口在实现上分为两步：第一步根据日期与时段从 **`sys_resource`** 取出候选资源；第二步调用 **`BookingFeignClient`** 访问 **booking-service** 的 **`GET /internal/bookings/conflicting-resource-ids`**，将返回的 **ID** 集合从候选集中剔除。**`BookingFeignClient`** 的 **`url`** 由 **`booking.service.url`** 指定，默认 **`http://127.0.0.1:9003`**，**不经 9000**，从而避免内部接口被误暴露给公网。若 **Feign** 调用失败，应有降级策略（如返回错误码并记录日志），避免前台静默展示错误数据。时序图可参考 **`docs/thesis/diagrams/05-sequence-resource-feign.md`**。

### 5.5 预定审核模块（Reservation and Review Module）

**booking-service** 中，**`BookingController`** 处理预约提交、列表与取消；**`ApprovalController`** 处理审批通过/驳回；**`BookingInternalController`** 仅对内提供冲突 **ID** 查询。预约提交路径在进入数据库事务前，通过 **Redisson** 获取分布式锁（资源粒度或业务自定义 **key** 以代码为准），使用 **`tryLock(wait, lease)`** 避免无限等待；持锁期间完成**时段合法性校验、与已有记录冲突检查、插入 `sys_booking`** 等步骤，最后在 **`finally`** 中释放锁。审批操作应校验操作者角色与预约当前状态，防止重复审批。内部冲突查询接口应对 **`date、startTime、endTime`** 做解析与校验，返回 **JSON** 数组形式的 **ID** 列表。预约提交流程可参考 **`docs/thesis/diagrams/04-sequence-booking-submit.md`**。

### 5.6 前端开发与构建模块（Front-End Development and Build Module）

**demovue3** 采用 **Vue Router** 划分登录页、资源查询页、预约页、审批页与管理页等；**Ant Design Vue** 提供表格、表单与消息反馈组件，减少手写样式成本。**`src/config/api.js`**（或等价模块）将 **`apiUrl`** 与 **`import.meta.env.VITE_API_BASE`** 拼接，使开发与生产仅通过环境变量区分网关地址。**`npm run build`** 生成 **`dist`** 后，可由 **Nginx** 以 **`root`** 指向该目录，并通过 **`location /api/`** **`proxy_pass`** 到 **`http://127.0.0.1:9000/`**，实现前后端同源策略下的联调与演示。若部署到 **HTTPS** 域名，需确保证书配置与 **`VITE_API_BASE`** 一致，避免混合内容被浏览器拦截。

### 5.7 非功能性需求实现（Non-Functional Requirements Realization）

**配置管理**：各服务 **`application.yml`** 中区分 **`spring.profiles.active`**，生产配置通过环境变量或外部文件注入数据库与 **Redis** 口令，避免写入 **Git**。**健康检查**：在 **POM** 中引入 **Actuator** 后，可开放 **`/actuator/health`** 供运维探活（生产应结合 **Spring Security** 或网络策略限制访问）。**内部接口安全**：**`/internal/**`** 仅在 **booking-service** 暴露，且不出现在 **Gateway** 路由表；防火墙或安全组层面可限制仅内网 **IP** 访问 **9003**。**构建与交付**：后端 **`mvn clean package -DskipTests`** 生成各服务 **jar**；建议启动顺序 **user → booking → resource → gateway**，以减少 **Feign** 与路由在启动瞬间的失败重试。

### 6.1 功能需求测试（Functional Requirements Testing）

功能测试采用**黑盒**思路，依据 **`docs/thesis/TEST_CASES.md`** 中的用例表逐条执行：每条用例应包含**前置条件、操作步骤、期望结果、实际结果、截图或日志编号**等字段。覆盖范围建议至少包括：**用户注册与登录、改密、非法口令提示**；**管理员用户增删与 Excel 导入的异常行处理**；**资源新增、启用停用后前台列表变化**；**可用资源查询在存在冲突预约时的过滤正确性**；**预约提交成功、重复时段拒绝、取消与审批状态流转**等。对跨服务场景，应重点验证 **resource-service** 在 **booking-service** 不可用或返回错误时的表现（如是否返回明确错误码、是否不写脏数据）。测试环境信息（**OS、JDK、Node、MySQL、Redis** 版本，各服务端口）应记录在表头，便于他人复现。

**稳定性与安全冒烟**：抽查 **Actuator** 健康端点是否返回 **`UP`**；确认 **`/internal/**`** 无法通过 **9000** 从外网访问；检查生产配置是否未误入版本库。**联调问题回归**：对曾出现的**网关与业务重复 CORS**、**服务启动顺序依赖**等问题，在测试报告中以「现象—根因—修复—复测结论」四段式记录，体现非功能需求在迭代中的落实。

### 6.3 本章小结（Chapter Summary）

本章说明了功能测试用例的组织方式及非功能与性能测试的实施要点，强调与 **`demospringboot`** 的对照实验数据须在定稿前按实测填写；测试结论应与第 3 章需求及第 5 章设计相互印证。

## 第 7 章　总结与展望

### 7.1 本文总结（Conclusions）

本文围绕**高校教学资源预约**这一具体业务，完成了从需求分析、概要设计、详细设计与实现到系统测试的完整工程闭环：后端基于 **Spring Boot 3** 与 **Spring Cloud 2023** 拆分为 **gateway-service、user-service、resource-service、booking-service**，通过 **Spring Cloud Gateway** 统一 **`/api/**`** 外网入口与 **CORS**；通过 **OpenFeign** 实现 **resource-service** 对 **booking-service** 内部冲突查询的复用；通过 **MySQL** 与 **MyBatis-Plus** 完成结构化持久化；通过 **Redis** 与 **Redisson** 在预约提交链上提供分布式互斥；前端采用 **Vue 3 + Vite + Ant Design Vue** 完成主要交互界面。工程保留 **demospringboot** 单体版本，使论文能够在**相同数据集**下讨论单体与微服务在路由跳数、部署单元与观测粒度上的差异，并以 **`docs/thesis`** 中的用例与实验模板支撑可复现叙述。

### 7.2 未来工作（Future Work）

当前系统在「可演示、可撰写」目标下已趋完整，但与生产级交付仍有距离：**身份认证**可演进为在 **Gateway** 过滤器中统一校验 **JWT**，业务服务仅信任网关注入的用户上下文；**服务发现与配置**可引入 **Nacos** 或同类组件，避免在 **`application.yml`** 中硬编码下游 **`URI`**；**接口契约**可进一步统一为 **`common-lib` 中的 `Result` 封装**，便于前端集中处理错误码；**可观测性**可接入 **Micrometer + Prometheus**、分布式追踪（如 **OpenTelemetry**）以缩短跨服务排障时间；**安全**层面可对 **Gateway** 增加限流与 **IP** 访问控制，并对 **Feign** 内网端口施加防火墙策略。上述工作可作为后续毕设迭代或课程设计的延续方向。
