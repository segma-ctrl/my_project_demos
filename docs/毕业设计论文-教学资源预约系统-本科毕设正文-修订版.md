## 摘要

高校里会用到的**教室、实验室、报告厅**这类教学资源，时间上往往挤在几段固定课点里，到了选课、集中做实验的时候，访问又会一下子顶上来，所以后台能不能扛住并发、前台能不能把「谁约了哪一间」说清楚，其实都挺关键的，传统那种**单体 Web** 把所有模块塞在一个进程里，一开始开发是省事的，可模块越堆越多以后，想单独扩一块、单独发一版，就会慢慢变得吃力。

本文做的，就是围绕**教学资源预约**这条业务线，把系统做成**前后端分离**的，后端走**基于 Spring Cloud Gateway 的微服务**这一套；前台上手用的是 **Vue 3 + Vite + Ant Design Vue**，后端按领域拆成 **user-service（用户与认证侧）、resource-service（资源与后台资源维护侧）、booking-service（预约、审批以及和 Redis 打交道的侧）**，外面再由 **gateway-service** 把 `/api/**` 这一层路由收进来，把**跨域（CORS）**也放在网关这一层统一处理，免得下游服务再写一遍头、浏览器那边又判失败；持久化用的是 **MySQL**，预约高峰那里上了 **Redis + Redisson**，用**分布式锁**把「同一时刻多个人抢同一时段」这种竞态兜住；资源这边查「这段时间到底还能约哪些教室」的时候，又通过 **OpenFeign** 去调 **booking-service** 暴露出来的**内部 REST**，把**时段冲突**算清楚再返回给页面。

论文里会写到：需求是怎么拆的、总体怎么划服务、库表和关键流程怎么设计、代码工程里几个模块各自干什么、功能测试怎么做的、以及**单体 demospringboot** 和 **platform 微服务**对照实验可以怎么填表，部署到云主机、**Nginx** 反代、`VITE_API_BASE` 指到域名这些也会点到；系统本人在本地已经用网关把几条主流程跑通过，作为本科毕设的工程体量，是能站得住脚的。

**关键词**：教学资源预约；微服务；Spring Cloud Gateway；OpenFeign；Redis；Vue 3

## Abstract

Classrooms, laboratories, and lecture halls on campus tend to be used in concentrated time slots and see bursty traffic when students book or change plans. This thesis describes the design and implementation of a **teaching resource reservation system** that adopts a **microservice architecture** with **Spring Cloud Gateway** as the single entry for browser traffic. The front end uses **Vue 3, Vite, and Ant Design Vue**; the back end comprises **user-service, resource-service, and booking-service**, fronted by **gateway-service** for routing and CORS. **MySQL** stores persistent data; **Redis with Redisson** supports distributed locking in reservation flows; **OpenFeign** lets **resource-service** query **booking-service** over an internal HTTP API to compute **time-slot conflicts**. Requirements, architecture, data design, implementation notes, testing, deployment, and an outline for comparing the monolithic and microservice variants are included.

**Keywords**: resource reservation; microservices; Spring Cloud Gateway; OpenFeign; Redis; Vue 3

## 第 1 章 绪论

### 1.1 为什么要做这么一套系统

一方面，学校里的**教室、实验室、报告厅**本来就是稀缺资源，如果还用纸质登记、群里接龙、各学院各一套表，信息对不齐的时候，**重复占用**、**谁说了算不清楚**这类矛盾就会出现；另一方面，把预约搬到网上以后，管理员能按角色看名单、能启用停用某间教室，师生能在页面上直接看到「这段时间还能不能约」，对管理成本是实打实能降下来的，所以做一个**教学资源预约**的系统，本身就有应用价值。

技术上还有一层意思：很多学校的老系统一开始是**单体 Spring Boot** 一把梭的，能跑，但人一多、模块一多，**发布粒度粗、改一处牵一片**的问题就会浮出来，把同一套业务用 **Spring Cloud** 拆成几个能独立起停的服务，外面再挂一个 **Spring Cloud Gateway**，其实是现在工业界很常见的一种折中——复杂度和运维成本会上来一点，但边界清楚了以后，写论文、答辩的时候，也就能把「为什么拆、拆完谁调谁」讲圆，所以本文在工程上保留了 **demospringboot** 那条单体线，又做了 **platform** 这条微服务线，后面第 7 章对比实验也有东西可写。

### 1.2 别人大致做到哪一步了（写法上留给你补文献）

国内国外高校信息化里，**教务、一卡通、实验室管理**里带预约子模块的已经不少，有的偏流程、有的偏移动端小程序；微服务、**API 网关**、**Redis** 做缓存或锁，在近几年工程文章里也很常见，**Spring Cloud Gateway** 作为基于 WebFlux 的网关实现，常被拿来和「统一入口、统一鉴权、统一限流」这类需求绑在一起说[2]；**OpenFeign** 这种声明式 HTTP 客户端，用来让 Java 里调远程像调本地方法一样，能减少很多样板代码；**Redisson** 在 **Redis** 之上把分布式锁封装好了，预约、抢票这类场景里引用很多[5]；前端 **Vue 3** 配 **Vite**，和 **REST + JSON** 的后端搭前后端分离，也是现在本科生毕设里很主流的一条技术栈[3]。

## 第 2 章 需求分析与总体方案

### 2.1 角色与大致能干什么

系统里主要碰到的角色，可以概括成**学生、教师、管理员**这几类，具体谁能审批、谁能改资源，还是以 **`auth_user` 表里的角色字段**和你在业务里写的规则为准；学生、教师这边，一般会有**注册、登录、改密码**，能**翻资源列表、按日期时段去约**，能在「我的预约」里看到**待审批 / 已通过 / 驳回 / 已取消**这些状态，规则允许的话还能**取消**；有人要审的时候，就到**审批列表**里对单条做**通过或驳回**，状态回写到 **booking** 那边以后，资源页上「这段时间还能不能约」也会跟着变；管理员这边，则要能**管用户**（列表、加人、删人、导入模板那套）、**管教室/实验室资源**（增删改、启用停用），把底表数据维护住了，前面的预约才不会乱。

### 2.2 功能需求拆开说

**用户与认证这条线**，要有注册、登录、改密，管理员要能维护用户，有的学校还会要**批量导入 Excel**，这些接口在网关里会转到 **user-service（9001）** 上去；**资源这条线**，后台要能维护 **sys_resource** 一类表里的资源，前台用户约之前要能查到「哪些还能约」，其中「还能不能约」又和预约记录有关，所以 **resource-service（9002）** 会跟 **booking-service（9003）** 打交道；**预约与审批这条线**，提交预约、列我的预约、取消，以及审批列表、通过、驳回，都落在 **booking-service**，和 **Redis / Redisson** 最近的也是这一块。

### 2.3 非功能需求：能跑、能扛、别乱、好改

**可用性**这块，希望某个服务挂了的时候，日志里能看出来，**Spring Boot Actuator** 的 **health** 也能点一下心里有数，网关后面如果某个端口没起来，前端至少别 silent fail，能有个明确错误；**性能**这块，高峰几个人同时点「提交预约」，不能把库写花，所以会有**分布式锁**、也会有数据库里该唯一的地方要唯一；**安全**这块，生产库密码别写死在 Git 里，**内部 Feign** 那条 **`/internal/bookings/conflicting-resource-ids`** 别暴露到公网网关路由上，这些在论文里都要点到；**可维护性**这块，前后端分开了，服务边界切开了，以后真要把审批流改复杂，至少知道该动哪个 jar。

### 2.4 总体方案：为什么拆成三个业务服务加一个网关

一方面，**用户、资源、预约**三块业务变更节奏本来就不一样，硬塞在一个进程里，发布的时候容易「为了改一个小按钮把整个后台重启一遍」；另一方面，**预约**和 **Redis 锁**绑得紧，**资源查询**又经常要读库还要问预约，把 **booking-service** 当成预约数据的「权威侧」，**resource-service** 用 **OpenFeign** 去拉冲突列表，比在两个服务各写一套占用逻辑要干净；再一方面，浏览器只访问 **gateway-service（9000）**，**CORS**、以后真要上的 **JWT 校验**，都可以往网关这一层收，前端 **`VITE_API_BASE`** 只配一个根地址，环境好切。

## 第 3 章 技术基础与选型说明

### 3.1 Spring Boot 与 Spring Cloud

**Spring Boot** 把依赖版本、自动配置、内嵌 Tomcat 这些事打包好了，写业务的人能少配很多 XML，毕设周期里上手快[1]；**Spring Cloud** 这一族，解决的是分布式里常见的那类问题，本课题里实际用到的，主要是跟 **Gateway**、**OpenFeign** 相关的 starter，版本上要和 **Spring Boot 3.x** 对齐，不然启动阶段就会各种不兼容。

### 3.2 Spring Cloud Gateway 当作统一入口

**API 网关**摆在浏览器和微服务集群中间，干的事无非是**把 URL 转发到对的机器**、顺带做**认证、限流、跨域**这些横切的东西；**Spring Cloud Gateway** 用 **Route + Predicate + Filter** 这套模型配路由，底层是 WebFlux 那一套，和 Boot 3 能搭在一起[2]；本课题里所有对外 **`/api/**`**，先到 **9000**，再按路径分到 **9001～9003**，前端开发时 **`http://localhost:5173`** 访问页面，接口打到 **`http://localhost:9000`**，靠网关返回的 **`Access-Control-Allow-Origin`** 头才能过浏览器的跨域检查，这里有个工程上踩过的坑：**网关已经写了 CORS，user-service 里就不要再配一层 WebMvc 的 CORS**，否则响应头里同一个字段出现两遍，Chrome 里会表现为 **200 但 fetch 进 catch**，看起来像「后端没起」，其实是头重复了，写论文时可以把这条写进「问题与解决」。

### 3.3 OpenFeign：服务之间用 HTTP 说话

**OpenFeign** 让你在接口上写 **`@FeignClient`**、在方法上写 **`@GetMapping` / `@PostMapping`**，由框架去拼 HTTP 请求、做序列化，**resource-service** 里的 **`BookingFeignClient`** 就是这么指向 **booking-service** 的 **`booking.service.url`**（默认 **`http://127.0.0.1:9003`**）的；这条调用**刻意不经网关**，因为那是给浏览器用的入口，内部流量走内网或本机回环就够了。

### 3.4 Redis、Redisson 与分布式锁

**Redis** 做缓存、做会话、做分布式协调都行，本课题里和预约强相关的是 **Redisson** 提供的 **RLock**，在 **`tryLock`** 拿不到锁的时候直接走「资源忙、请重试」那条业务分支，比单纯靠数据库抛唯一约束异常，对用户来说友好一点[5]；锁的 key 怎么拼、超时设多少，要和你的资源 id、时段字段对齐，答辩时老师问到「锁粒度」要能答上来。

### 3.5 Vue 3、Vite、前后端分离

页面上用的是 **Vue 3** 组合式写法，组件里有 **`fetch(apiUrl('/api/login'))`** 这一类调用，**`apiUrl`** 封装在 **`demovue3/src/config/api.js`**，读的是 **`import.meta.env.VITE_API_BASE`**，本地 **`.env.development`** 里配 **`http://localhost:9000`**，生产构建前把变量改成 **`https://你的域名`**，打出来的 **`dist`** 就能交给 **Nginx** 静态托管[3]。

### 3.6 REST、JSON 与单体对照

接口形态上走的是 **HTTP + JSON**，字段名前后端对齐，浏览器 F12 里一眼能看懂；仓库里 **demospringboot** 那条单体线还在，**platform** 是拆完以后的版本，两篇对照写进第 7 章的表，就能把「进程数变多了、延迟多了网关一跳」这类现象记下来，不追求特别严谨的压测，本科论文里**有数、有解释**就已经加分了[6][7]。

## 第 4 章 系统架构与接口设计

### 4.1 分层：从浏览器到 MySQL、Redis

浏览器里跑的是 **Vue** 打出来的单页应用；往外发的 **`/api/**`** 流量进 **gateway-service（9000）**；再往里，**9001** 管人，**9002** 管资源并会 **Feign** 问 **9003**，**9003** 管预约审批、连 **MySQL**、连 **Redis**；**MySQL** 里库名本课题用的是 **`wwq_bs`**，表上有 **`auth_user`、`sys_resource`、`sys_booking`** 这些，和单体阶段能对上号，迁移成本小。

**图 4-1**（请插入）：`docs/thesis/diagrams/01-system-architecture.md` 里那张总体架构，导出 PNG 贴进来。

### 4.2 网关路由：路径怎么分到各服务

网关 **`application.yml`** 里 **`spring.cloud.gateway.routes`** 一段，把 **`/api/login`、`/api/register`、`/api/changePassword`** 指到 **user-service**，把 **`/api/admin/user/**`** 也指过去；把 **`/api/resource`** 以及 **`/api/admin/list`、`add`、`disable`、`enable`** 指到 **resource-service**；把 **`/api/booking/**`、`/api/approval/**`** 指到 **booking-service**；**`/actuator/health`** 在网关自己能点，用来瞄一眼网关活着没有，更细的下游健康可以以后加；完整路径表仓库 **`docs/thesis/API.md`** 里已经列了一版，论文里可以摘一张「节选表」放进正文。

|--------------|----------------|

### 4.3 Feign 内部：`conflicting-resource-ids` 这条链

用户在前台选了一个日期、起止时间，点「查还能约的资源」时，**resource-service** 除了查 **`sys_resource`**，还要知道这段时间里**哪些资源 id 已经在预约表里占上了**，这件事只有 **booking-service** 最清楚，所以 **`BookingFeignClient`** 会去 **GET `/internal/bookings/conflicting-resource-ids?date=…&startTime=…&endTime=…`**，拿到 **`List<String>`** 以后在内存里把冲突的 id 滤掉，再包装成 JSON 给前端；这条链路**不暴露在网关路由**里，论文里要强调**生产环境别把它端口开到公网**。

**图 4-2**（请插入）：`docs/thesis/diagrams/05-sequence-resource-feign.md` 的时序图。

### 4.4 和单体 **demospringboot** 的关系

**demospringboot** 默认 **8080** 一个进程扛所有 **`/api/**`**，**platform** 把它拆成四个进程加网关，**表结构可以共用**，这样你做对比实验的时候，数据库不用换两套，只要把请求分别打到 **8080** 和 **9000**，记延迟、记失败率，就能写一段「工程上多进程拆分带来的代价与收益」，比空讲概念要实在。

### 4.5 创新点（答辩时可以直接说）

**第一个方面**，把**网关统一接入**、**预约数据权威在 booking**、**资源侧用 Feign 拉冲突**这三件事串成一条完整链路，资源展示和占用判断不会各写一套逻辑；**第二个方面**，预约提交链路上**上了 Redisson 分布式锁**，多实例部署的时候，**竞态**能兜一层，再配合第 7 章的**简单并发或重复点击实验**，就有图有数。

## 第 5 章 数据库与核心业务流程

### 5.1 核心表与 ER 示意

**`auth_user`** 管登录名、密码、角色；**`auth_student`、`auth_teacher`、`auth_manager`** 一类扩展表按你学校业务可以挂学号工号；**`sys_resource`** 存教室名、类型、地点、容量、状态；**`sys_booking`** 存哪个人约了哪个资源、从几点到几点、状态是待审还是通过；**`booking_cleanup`** 若你有定时清理任务，可以记清理批次或日志，具体字段以你库为准。

**图 5-1**（请插入）：`docs/thesis/diagrams/06-er-core-tables.md`。

### 5.2 登录、预约两条主链（文字跟图对齐就行）

**登录这条链**，浏览器 POST **`/api/login`** 到 **9000**，网关转到 **9001**，**AuthController** 里 **`@PostMapping("api/login")`** 去 **`auth_user`** 里查用户名，比密码、比角色，把 **`status`、`message`** 塞回 JSON，前端 **`Login.vue`** 里判断 **`result.status`** 为真就把 **`localStorage`** 写上再 **`router.push('/home')`**，这条链 **`docs/thesis/diagrams/03-sequence-login.md`** 里有图。

**预约提交这条链**，POST **`/api/booking/add`** 进 **booking-service**，服务里先 **`tryLock`**，拿到了再写 **`sys_booking`**，写完了 **`unlock`**，拿不到就告诉用户这边忙、换个时间或重试，图在 **`04-sequence-booking-submit.md`**。

### 5.3 冲突检测与锁：两个层面别混着说

**冲突检测**是业务正确性问题，**booking-service** 的 **`listConflictingResourceIds`** 把和给定区间重叠的预约都扫出来，返回占用的资源 id；**分布式锁**是并发安全问题，防止两个请求同时以为自己都能写进同一条时段，两件事在论文里分开写，答辩不容易被问糊涂。

## 第 6 章 系统实现与工程结构

### 6.1 仓库里目录怎么摆的

根目录下 **`platform/`** 是 Maven 父工程，子模块里有 **`common-lib`（统一 `Result`、异常处理一类）**、**`gateway-service`、`user-service、resource-service、booking-service`**；前端在 **`demovue3/`**；毕设用的图、接口表、测试表、部署说明在 **`docs/thesis/`**，论文里插图、插表可以反复引用那套材料；单体对照还在 **`demospringboot/`**。

### 6.2 端口、启动顺序、配置里要盯的数

**user-service** 配在 **9001**，**resource-service** 在 **9002**，**booking-service** 在 **9003**，**gateway** 在 **9000**，本地起的时候顺序最好是 **user → booking → resource → gateway**，因为 **resource** 起 Feign 的时候 **9003** 得已经在了，**gateway** 最后起，否则一进来转发全是 **502**；**`application.yml`** 里 **JDBC URL**、**Redis host**、**`booking.service.url`** 生产环境都要改成你服务器上真实能连到的地址，密码别提交到 Git。

### 6.3 各服务里几个关键的 Java 入口

**user-service**：**`AuthController`** 管登录注册改密以及 **`/api/admin/user/**`** 管理员用户接口；**resource-service**：**`ResourceController`** 里 **`/api/resource`** 和 **`/api/admin/*`** 资源维护；**booking-service**：**`BookingController`、`ApprovalController`** 对外，**`BookingInternalController`** 对 Feign 暴露 **`/internal/bookings/conflicting-resource-ids`**；**gateway** 只有路由和 **globalcors**，没有业务表。

### 6.4 前端怎么配接口根路径

**`demovue3/src/config/api.js`** 里 **`API_BASE`** 读环境变量，**`apiUrl('/api/login')`** 这种拼法，开发时走 **9000**，生产走 **Nginx** 同域 **`/api`** 也行，把 **`VITE_API_BASE`** 留空配合 **Vite proxy** 也是一种写法，你论文里写清楚你最终选了哪种即可。

### 6.5 公共库、返回体不统一这类「诚实的小毛病」

**common-lib** 已经在部分接口上用了 **`Result`**，但登录那块还有 **`Map`** 形态的历史写法，论文里不用遮掩，写成「后续工作里会把返回体统一掉」，老师反而觉得你知道问题在哪；定时清理若用了 **`@Scheduled`**，类名、Cron、扫的表，点到为止，大段 SQL 贴附录。

## 第 8 章 总结与展望

本文把**教学资源预约**这套业务，用 **Vue 3 + Spring Cloud Gateway + 三个 Spring Boot 微服务**落成了一个能跑、能测、能部署的工程，**MySQL** 存业务，**Redis + Redisson** 扛预约并发，**OpenFeign** 把资源查询和预约冲突绑在一起，**网关**把路由和 **CORS** 收拢，和仓库里 **`platform`、`demovue3`** 的代码是能对上的。

不足也很直白：**JWT** 还没挂到 **gateway** 上，**Nacos** 一类注册配置中心也没接，**返回体**还没完全统一成 **`Result`**，对比实验若只做了手工点几次，严谨性也有限；以后若能加上**消息队列**削峰、把**链路追踪**打通、把**内部接口**放到内网策略里，这个毕设就能自然延伸成「下一阶段要做的事」，答辩收尾也会顺。
