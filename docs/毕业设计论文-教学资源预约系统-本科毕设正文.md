## 摘要

高校教室、实验室及报告厅等教学资源具有时段性强、并发访问集中的特点，传统单体 Web 系统在扩展与维护上易出现瓶颈。本文围绕「教学资源预约」业务，完成了一套**前后端分离**、**基于 Spring Cloud Gateway 的微服务架构**的系统设计与实现。前端采用 **Vue 3 + Vite + Ant Design Vue**；后端按领域拆分为 **用户服务（user-service）、资源服务（resource-service）、预约与审批服务（booking-service）**，并由 **gateway-service** 统一对外路由与跨域处理；数据层使用 **MySQL** 持久化，**Redis + Redisson** 支撑预约场景下的并发控制；资源服务通过 **OpenFeign** 调用预约服务内部接口，实现跨服务的**时段冲突检测**。论文给出了需求分析、总体与详细设计、数据库与接口说明、功能测试与部署方案，并对单体与微服务方案进行了对比实验框架说明。系统已在本地与网关模式下联调通过，可作为本科毕业设计的完整工程案例。

**关键词**：教学资源预约；微服务；Spring Cloud Gateway；OpenFeign；Redis；Vue 3

## Abstract

Teaching resources such as classrooms and laboratories exhibit strong time-slot characteristics and bursty concurrent access. This thesis presents the design and implementation of a **university teaching resource reservation system** using a **microservice architecture** with **Spring Cloud Gateway** as the unified entry. The front end is built with **Vue 3, Vite, and Ant Design Vue**; the back end is split into **user-service, resource-service, and booking-service**, orchestrated by **gateway-service** for routing and CORS. **MySQL** stores business data; **Redis with Redisson** supports concurrency control in reservation flows; **OpenFeign** enables **resource-service** to query conflicting resource identifiers from **booking-service** via an internal REST API. The thesis covers requirements, architecture, detailed design, testing, deployment, and a comparative experiment outline between monolithic and microservice deployments.

**Keywords**: resource reservation; microservices; Spring Cloud Gateway; OpenFeign; Redis; Vue 3

## 1 绪论

### 1.1 研究背景与意义

高等教育规模持续扩大，**教室、实验室、报告厅及设备**等教学资源需要在时间维度上被合理分配。手工登记或分散表格管理存在信息不透明、审批链长、**高峰时段重复占用**等问题。信息化预约系统能够提高资源利用率、规范审批流程，并为管理决策提供数据基础。

从技术演进看，早期校园信息系统多采用**单体架构**，开发与部署简单，但随着模块增多，**编译耦合、发布粒度粗、横向扩展困难**等问题逐渐显现。微服务架构将系统按业务能力拆分为多个可独立部署的服务，配合 **API 网关**统一安全与路由，有利于团队分工与渐进式演进[6][7]。因此，以本科毕业设计为周期，完成「教学资源预约」课题下的**微服务化实现**，具有工程训练价值，也能形成可写入论文的完整案例。

### 1.2 国内外研究现状

**（1）校园信息化与预约类系统**  
国内外高校普遍建设教务、一卡通、实验室管理等系统；预约功能常作为子模块存在。研究多关注流程建模、移动端入口（如微信小程序）与消息通知等，对**底层架构是否采用微服务**描述不一。

**（2）微服务与 API 网关**  
工业界广泛采用 **Spring Cloud** 生态构建微服务；**Spring Cloud Gateway** 基于 WebFlux，适合作为边缘流量入口，完成路由、过滤与跨域等横切能力[2]。文献与工程实践普遍强调**服务边界划分、接口版本管理与可观测性**[6]。

**（3）并发控制与缓存**  
对「同一资源同一时段仅允许一个有效预约」等约束，工程上常结合数据库唯一约束与 **Redis 分布式锁** 降低热点冲突下的失败重试成本；**Redisson** 在 Java 生态中提供了可编程的锁与看门狗等语义[5]。

**（4）前后端分离**  
**Vue 3** 组合式 API 与 **Vite** 工具链提升了前端工程化效率，与 **REST** 风格后端组合是主流前后端分离方案[3]。

## 2 相关技术与理论基础

### 2.1 Spring Boot 与 Spring Cloud

**Spring Boot** 通过约定优于配置、起步依赖与内嵌容器，简化了企业级应用的构建与部署[1]。**Spring Cloud** 为分布式系统中的常见问题提供组件化支持；本课题使用其中与网关、声明式 HTTP 客户端相关的部分。

### 2.2 Spring Cloud Gateway 与 API 网关

**API 网关**位于客户端与微服务集群之间，承担路由转发、认证鉴权、限流与跨域等职责。**Spring Cloud Gateway** 通过 `Route`、`Predicate`、`Filter` 模型描述路由规则，可与 Spring Boot 3 体系协同工作[2]。本系统将浏览器访问的 `/api/**` 流量统一接入网关端口 **9000**，再分发至 9001～9003。

### 2.3 OpenFeign 与服务间调用

**OpenFeign** 以接口与注解声明远程 HTTP 调用，由框架生成代理并完成编解码，降低服务间协作的样板代码量。本课题中 **resource-service** 通过 Feign 调用 **booking-service** 的 **内部 REST** 接口，用于查询给定时段内与已有预约冲突的资源标识集合。

### 2.4 Redis / Redisson 与分布式锁

**Redis** 作为内存数据结构与缓存中间件，广泛用于会话、缓存与分布式协调场景。**Redisson** 在 Redis 基础上封装了 Java 侧的分布式锁、信号量等 API，适合在预约提交等热点路径上实现**互斥与防重入**[5]。

### 2.5 Vue 3 与前后端分离

前端采用 **Vue 3** 与 **Vite** 构建单页应用，通过 `fetch` 调用网关暴露的 REST 接口；生产环境可将静态资源置于 **Nginx**，接口基地址通过构建期环境变量 `VITE_API_BASE` 指向网关或反向代理路径[3]。

### 2.6 REST 风格与 JSON 数据交换

各服务对外以 **HTTP + JSON** 为主进行数据交换，符合 **RESTful** 设计思想中「资源定位 + 统一接口」的实践形态[7]。请求与响应体字段命名保持前后端一致，便于使用浏览器开发者工具进行联调与问题定位。

### 2.7 单体与微服务对比（为第 9 章与实验铺垫）

**单体应用**将所有模块部署于同一进程，共享同一数据源与配置，开发与调试路径短；但当模块边界模糊时，易出现「改一处动全身」的回归风险。**微服务**将变化频率不同的业务能力拆开，有利于团队并行开发与独立发布，但引入网络调用、分布式事务与运维复杂度[6][7]。本课题保留 **demospringboot** 单体工程作为对照，便于在论文中开展**对比实验**（见 `docs/thesis/EXPERIMENT.md`）。

## 3 系统需求分析

### 3.1 业务角色与用例概述

系统涉及的主要角色包括：**学生、教师、管理员**（具体权限以 `auth_user` 中角色字段及业务规则为准）。学生/教师可进行资源浏览、预约申请、查看个人预约与取消；教师或具备审批权限的角色可进行**审批**；管理员可进行**用户与教学资源**的维护。

### 3.2 功能性需求

（1）**用户与认证**：注册、登录、修改密码；管理员维护用户列表、导入导出等。  
（2）**资源管理**：资源的增删改查、启用/停用；用户侧按条件查询可用资源。  
（3）**预约与审批**：提交预约、我的预约列表、取消预约；审批列表、通过、驳回。  
（4）**跨服务协作**：在指定日期与起止时间内，资源查询结果应排除与**已存在预约冲突**的资源。

### 3.3 非功能性需求

（1）**可用性**：单服务故障时，应能通过日志与健康检查定位；网关应对下游不可用返回明确错误。  
（2）**性能**：高峰并发下预约提交不应出现大面积数据不一致；采用缓存与分布式锁降低冲突概率。  
（3）**安全**：生产环境数据库口令等敏感配置外置；内部 Feign 接口不应暴露于公网。  
（4）**可维护性**：前后端分离、服务职责清晰，便于迭代。

### 3.4 用例与流程的文字化描述（可配用例图）

**学生/教师**：注册账号并经管理员或业务规则审核后登录；在资源列表中按日期与时段筛选可预约资源；提交预约后可在「我的预约」中查看状态（如待审批、已通过、已驳回、已取消）；在规则允许时发起取消。  

**审批人员**：在审批列表中查看待办记录，对单条记录执行通过或驳回；操作结果回写预约状态并影响资源在该时段的可用性展示。  

**管理员**：维护用户（增删改、批量导入）、维护教学资源（增删改、启用/停用），保障基础数据与预约业务一致。

## 4 系统总体设计

### 4.1 逻辑架构与微服务划分

系统分为**客户端层、接入层、业务微服务层、数据与中间件层**。客户端为浏览器中的 Vue 应用；接入层为 **gateway-service（9000）**；业务层包括 **user-service（9001）、resource-service（9002）、booking-service（9003）**；数据层为 **MySQL**，**Redis** 供预约服务使用。

**图 4-1**（请插入）：总体逻辑架构图 —— 见 `docs/thesis/diagrams/01-system-architecture.md` 中 Mermaid 导出。

### 4.2 网关路由与对外接口聚合

网关将对外路径按前缀与业务归属转发：登录注册与用户信息相关接口至 **user-service**；资源列表与用户侧资源查询至 **resource-service**；预约与审批至 **booking-service**。跨域策略配置在网关，避免与下游服务**重复写入 CORS 响应头**导致浏览器拒绝（本课题工程实践中已处理该类问题）。

**表 4-1 网关对外路径与转发目标（节选）**

| 路径模式 | 目标服务 |
|----------|-----------|
| `/api/login`, `/api/register`, `/api/changePassword` | user-service |
| `/api/admin/user/**` | user-service |
| `/api/resource`, `/api/admin/list` 等 | resource-service |
| `/api/booking/**`, `/api/approval/**` | booking-service |

完整表见仓库 `docs/thesis/API.md`。

### 4.3 内部协作与 Feign 调用关系

**resource-service** 在聚合「某时段可用资源」时，调用 **booking-service** 的 `GET /internal/bookings/conflicting-resource-ids`，参数为日期与起止时间；返回冲突资源 ID 列表后在资源侧过滤。该调用**不经网关**，由配置项 `booking.service.url` 指定直连地址。

**图 4-2**（请插入）：Feign 内部调用时序图 —— 见 `docs/thesis/diagrams/05-sequence-resource-feign.md`。

### 4.4 与单体版本的对应关系（论文创新表述可用）

仓库中 **demospringboot** 为早期单体实现，**platform** 为微服务拆分后的目标架构。二者可共用同一 **MySQL 库名与表结构**（如 `wwq_bs`），便于数据迁移与对照实验：在相同请求负载下，分别压测单体端口与网关端口并记录延迟与错误率，从**工程维度**说明微服务化的收益与成本。该对照可作为本科论文中「**架构演进与实验验证**」的组成部分。

### 4.5 创新点归纳（答辩可直接使用）

**创新点一**：提出并实现了「**网关统一接入 + 预约权威服务 + Feign 冲突查询**」的跨服务协作模式，使资源展示与预约占用解耦，降低重复业务逻辑。  

**创新点二**：在预约提交链路引入 **Redis/Redisson 分布式锁**，面向多实例部署场景提升并发安全性，并可与对比实验结合说明效果。

## 5 数据库与详细设计

### 5.1 概念模型与核心表

核心实体包括：**用户（auth_user）**、**学生/教师/管理员扩展表**、**教学资源（sys_resource）**、**预约记录（sys_booking）** 及与清理任务相关的 **booking_cleanup** 等。用户与预约、资源与预约为一对多关系。

**图 5-1**（请插入）：核心 ER 图 —— 见 `docs/thesis/diagrams/06-er-core-tables.md`。

### 5.2 关键业务流程设计

**登录流程**：浏览器 → 网关 → user-service → 数据库校验用户名、密码与角色匹配，返回 JSON 结果。参见 `docs/thesis/diagrams/03-sequence-login.md`。

**预约提交流程**：浏览器 → 网关 → booking-service → **尝试获取 Redisson 分布式锁** → 写库 → 释放锁；失败时返回冲突或提示重试。参见 `docs/thesis/diagrams/04-sequence-booking-submit.md`。

### 5.3 并发与冲突检测设计

（1）**跨服务冲突检测**：以 **booking-service** 为预约数据的权威来源，通过内部接口输出冲突资源 ID 集合；**resource-service** 负责与资源静态信息组合后返回前端，避免在多个服务重复维护占用逻辑。  

（2）**分布式锁**：在预约提交等临界区使用 **Redisson** 的 `tryLock` 语义，防止多实例下的竞态条件；锁的粒度与键设计应与业务字段（如资源 ID + 时段）一致，并在论文中说明**锁超时与失败分支**。

## 6 系统实现

### 6.1 开发环境与工程结构

- **JDK**：17  
- **构建**：Maven 多模块，父工程 `platform` 管理依赖版本  
- **前端**：Node.js + npm，Vite 开发服务器默认端口 5173  
- **工程路径**：后端 `platform/`；前端 `demovue3/`；论文素材 `docs/thesis/`  

各服务 `application.yml` 中配置数据源与 Redis；**生产环境**建议使用 `spring.profiles.active=prod` 与外部化配置，避免将真实口令写入版本库。

### 6.2 网关与用户认证相关实现要点

网关在 `application.yml` 中声明 `spring.cloud.gateway.routes`；全局 CORS 允许前端开发域名。用户服务中 **AuthController** 提供登录、注册、改密及管理员用户相关接口；返回体当前存在 **Map** 与 **统一 Result** 并存的情况，可在后续迭代中完全统一，论文中可记为「改进点」。

### 6.3 预约、审批与资源查询实现要点

- **booking-service**：`BookingController`、`ApprovalController` 暴露预约与审批 REST；`BookingInternalController` 暴露内部冲突查询接口。  
- **resource-service**：`ResourceController` 实现资源管理与用户查询；通过 **BookingFeignClient** 调用内部接口。  
- **前端**：`src/config/api.js` 使用 `VITE_API_BASE` 拼接 `/api/**` 请求地址，便于区分本地网关与生产域名。

### 6.4 公共模块与异常处理

**common-lib** 提供统一返回体 `Result` 与全局异常处理等横切能力，供 user-service 等依赖；论文中可说明该模块有利于**减少重复代码**与**统一错误语义**。若部分接口仍返回 `Map` 结构，可在「不足与改进」中写明后续统一为 `Result` 的计划。

### 6.5 定时与数据清理（可选小节）

单体与预约服务中可包含**定时任务**（如过期预约清理），用于释放长期占用或同步状态。论文中可简述触发周期、所涉表及与业务规则的关系；具体类名与 SQL 以仓库实现为准（注意论文中贴代码宜短而精，长代码放附录）。

## 8 系统部署与运行

### 8.1 部署拓扑

生产环境建议：**云主机**安装 MySQL、Redis；四个 Spring Boot 服务与网关同机或分机部署；**Nginx** 监听 443，静态资源托管前端 `dist`，`/api` 反向代理至 `127.0.0.1:9000`。拓扑图见 `docs/thesis/diagrams/02-deployment-topology.md`。

### 8.2 构建与启动顺序

1. `mvn clean package -DskipTests` 生成各服务 jar。  
2. 启动顺序：**user-service → booking-service → resource-service → gateway-service**。  
3. 前端：`VITE_API_BASE=https://你的域名`（或 `http://IP`）执行 `npm run build`，将 `dist` 部署至 Nginx `root`。

详细命令、防火墙与 CORS 注意点见 `docs/thesis/DEPLOYMENT.md` 与 `nginx.example.conf`。

## 9 结论与展望

本文完成了基于 **Spring Cloud Gateway** 的高校教学资源预约系统设计与实现，采用 **user / resource / booking** 三业务服务拆分，结合 **OpenFeign** 实现跨服务冲突检测，结合 **Redis/Redisson** 提升预约并发场景下的安全性，并通过 **Vue 3** 完成前后端分离界面。系统在功能测试与本地/网关联调中表现稳定；论文给出了部署与对比实验框架，便于在答辩中展示工程完整性。

**不足与展望**：（1）网关层 **JWT 统一鉴权** 尚未接入，后续可在登录后签发令牌并由网关校验；（2）配置中心与服务发现可采用 **Nacos** 等组件简化多环境运维；（3）可引入**消息队列**削峰填谷，将部分写库异步化；（4）对比实验可进一步使用 **JMeter** 固定并发模型采集响应时间与错误率曲线。
