## 摘　要

数字化校园背景下，**教室、实验室、报告厅**等资源的网上预约与审批已成为常见需求；传统登记方式易致**时段冲突、责任不清**，**单体 Web** 则在规模扩大后面临扩容与发版粒度偏粗等问题。微服务架构有利于按业务拆分与独立部署[10][11]。

本文基于 **Spring Boot 3** 实现**教学资源预约系统**：划分 **gateway-service、user-service、resource-service、booking-service**，经 **Spring Cloud Gateway（9000）** 统一 **`/api/**`** 路由与 **CORS**；**resource-service** 经 **OpenFeign** 调用 **booking-service** 内部接口获取**冲突资源 ID** 后过滤可用资源；**MySQL + MyBatis-Plus** 持久化，预约提交链使用 **Redis + Redisson** 分布式锁；前端 **Vue 3 + Vite + Ant Design Vue**，**`VITE_API_BASE`** 指向网关；保留 **demospringboot（8080）** 与 **platform** 作对照。论文给出需求与可行性、概要/详细设计、测试与对比实验思路，并展望 **JWT、Nacos** 等。图表与用例源文件见 **`docs/thesis/`**。参考文献 **42** 篇。

## Abstract

Digital campus initiatives call for efficient online booking of **classrooms, labs, and halls**; legacy workflows cause **conflicts and weak accountability**, while **monolithic Web** stacks scale and release coarsely. **Microservices** improve modularity and isolation[10][11].

This thesis implements a **Spring Cloud** reservation system on **Spring Boot 3** with **gateway-service**, **user-service**, **resource-service**, and **booking-service**; **Spring Cloud Gateway (9000)** routes **`/api/**`** and centralizes **CORS**. **resource-service** uses **OpenFeign** to **booking-service** for **conflicting resource IDs**. **MySQL** and **MyBatis-Plus** persist data; **Redis** and **Redisson** guard the booking path. The UI uses **Vue 3**, **Vite**, and **Ant Design Vue** with **`VITE_API_BASE`** at the gateway. The **demospringboot** monolith (**8080**) is kept for comparison with **platform**. The paper presents requirements, design, tests, experiments, and future work (**JWT**, **Nacos**). Artifacts live under **`docs/thesis/`**. **42** references.

**Keywords**: teaching-resource reservation; Spring Cloud Gateway; microservices; OpenFeign; Redis; Redisson; Vue 3

## 第 1 章　绪论

### 1.1 研究背景与意义（Research Background）

当前高校推进**数字化校园**与**教育信息化**，**教室、实验室、报告厅**等资源的分配与预约若仍依赖纸质或分散表格，易出现**利用率不高、时段冲突、核对成本高**等问题；将预约搬到线上并统一入口，有利于提升管理效率与透明度。

## 第 2 章　开发环境与相关技术

### 2.1 开发环境（Development Environment）

本课题采用**前后端分离 + 微服务**分层结构，各部分的开发环境如下。

（1）**前端（Web 端）**：以 **JavaScript** 为主要脚本语言（**Vue 3** 单文件组件），采用 **Vite** 作为构建与开发服务器，**Ant Design Vue** 作为组件库；工程目录为 **`demovue3`**，使用 **`npm install` / `npm run dev`** 进行依赖安装与本地联调，使用 **`npm run build`** 产出静态资源，并通过环境变量 **`VITE_API_BASE`** 将接口根地址指向 **Spring Cloud Gateway**。开发环境为 **Node.js 18 及以上**（建议 LTS 版本），本仓库依赖中 **Vue** 为 **^3.5.13**、**Vite** 为 **^6.0.3**、**ant-design-vue** 为 **^4.2.6**；联调与演示浏览器可选用 **Microsoft Edge** 或 **Google Chrome** 等现代浏览器，开发工具可选用 **Visual Studio Code** 或 **IntelliJ IDEA**（内置前端支持）。

（2）**网关与业务微服务（HTTP API）**：以 **Java** 为主要编程语言，**JDK 17**；采用 **Spring Boot 3.3.7** 与 **Spring Cloud 2023.0.4**（见父工程 **`platform/pom.xml`**），子模块包括 **gateway-service、user-service、resource-service、booking-service** 及公共模块 **common-lib**；对外与浏览器之间通过 **HTTP** 提供 **REST** 接口，请求与响应体采用 **JavaScript Object Notation（JSON）** 序列化传输。构建与依赖管理使用 **Apache Maven 3.8+**；开发工具以 **IntelliJ IDEA** 为主。**gateway-service** 监听 **9000** 端口，**user-service、resource-service、booking-service** 分别监听 **9001、9002、9003**（以各服务 **`application.yml`** 为准）。

（3）**微服务间内部调用**：**resource-service** 通过 **OpenFeign** 以声明式 **HTTP** 客户端方式调用 **booking-service** 暴露的内部 **REST** 接口（如冲突资源 **ID** 查询），与浏览器经网关访问外网入口的路径相区分；该调用默认直连 **`http://127.0.0.1:9003`**（配置项 **`booking.service.url`**），**不经 Gateway**，仍采用 **JSON** 作为载荷格式。开发工具与第（2）项相同。

（4）**数据库、中间件与文档环境**：业务数据使用 **MySQL 8.x** 存储，持久层采用 **MyBatis-Plus 3.5.10.1**；预约链路使用 **Redis**，在 **Java** 侧配合 **Redisson** 等组件。数据库可使用 **MySQL Workbench**、**DBeaver** 或 **`mysql`** 命令行客户端；**Redis** 可使用 **`redis-cli`** 或常用图形化工具。论文用 **API**、测试与部署说明及图表源文件集中于 **`docs/thesis/`** 与 **`docs/thesis/diagrams/`**；与微服务对照的**单体**工程为 **`demospringboot`**（**Spring Boot 3.3.7**，默认 **8080**），用于第 6 章对比实验。

### 2.2 微服务架构（Microservice Architecture）

本课题的 **platform** 工程采用**微服务**方式划分后端；微服务架构与**单体架构**在部署形态与演进路径上存在明显差异，下面分述其特点及适用边界，并归纳微服务带来的工程收益与额外成本。本仓库中 **demospringboot（8080）** 与 **platform（经 Gateway 9000 接入）** 并存，便于后文对照实验。

#### 2.2.1 单体架构模式（Monolithic Architecture）

**单体架构**是一种常见的传统形态：用户交互、业务规则、数据访问等模块被打包在同一部署单元（如单个 **Spring Boot** 可执行 **jar**）中，运行时处于同一进程空间，模块之间多以**进程内调用**方式协作。其优点是工程结构直观、本地调试与版本发布流程简单，在功能较少、团队规模较小的阶段**上手快、成本低**。随着需求迭代，业务模块持续增多，单体往往出现**耦合增强、编译与启动变慢、发版只能整体发布**等现象；当访问量上升时，扩容通常也只能**水平复制整个应用**，难以对热点模块做**精细化伸缩**。微服务与单体的对比及模块化收益在业界专著中已有系统阐述[10][11]。

#### 2.2.2 微服务架构模式（Microservice Architecture）

**微服务架构**将应用拆成一组**围绕业务能力构建、可独立部署**的小服务；各服务拥有相对清晰的边界，对外通过**轻量协议**（如 **HTTP REST**、消息队列等）协作，数据库与事务边界也可按服务拆分，从而把变更与故障尽量限制在局部。相较单体，微服务在实践中常被归纳出以下优点[10][11]：

（1）**可扩展性**：可按访问热点对单个服务扩容，而不必复制整套应用。  

（2）**敏捷与迭代**：不同服务可由不同模块并行演进，发布节奏相对独立，更贴近持续集成与交付的实践。  

（3）**容错与隔离**：单个服务异常时，影响面相对可控，定位范围缩小。  

（4）**可维护性**：单仓代码规模随服务拆分而分散，业务语义在仓库层面更易与团队分工对齐。  

与此同时，微服务也会引入**服务发现、链路追踪、配置管理、分布式一致性、集成测试复杂度上升**等问题[10][11]；因此需要配套的**网关、观测与规范化的服务间调用**等基础设施。本课题刻意控制范围：先落实 **Gateway 统一入口** 与 **OpenFeign** 声明式 **HTTP** 调用，将 **Nacos** 等组件留待展望，以降低毕设周期内的工程风险。

### 2.3 Spring Cloud 与网关及服务协作（Spring Cloud, Gateway, and Service Collaboration）

本课题后端以 **Java 17** 为基线，采用 **Spring Boot 3.3.7** 与 **Spring Cloud 2023.0.4**（见 **`platform/pom.xml`**），在「多 **jar**、单入口」的前提下完成路由、跨域与服务间协作；下面按**编程模型、组件边界、网关机制、Feign 调用**四层说明。

#### 2.3.1 Spring Boot 3 编程模型

**Spring Boot 3** 与 **Spring Framework 6** 对齐，以 **Jakarta EE** 命名空间替代原 **javax**，在依赖管理与可观测性等方面较 **2.x** 线更为统一[1]；官方亦提供 **AOT**、**native hints** 等面向云原生镜像的扩展路径。本课题未启用 **GraalVM Native Image**，但在 **Boot 3** 上构建多模块父工程，有利于与后续容器化、可观测性组件的渐进接入保持一致。

#### 2.3.2 Spring Cloud 组件边界与版本对齐

**Spring Cloud** 与 **Spring Boot** 之间存在**严格的版本对应关系**；本课题采用 **2023.0.x** 与 **Boot 3.3.x** 的 **BOM** 对齐，减少依赖冲突。实施阶段未引入 **Nacos、Sentinel** 等全家桶组件，而是优先使用与**外网入口路由、服务间 HTTP 协作**直接相关的 **Gateway、OpenFeign** 等能力，把注册中心与熔断限流留给第 7 章讨论，使正文叙述与仓库代码一一对应、避免「只写配置未落地」。

#### 2.3.3 Spring Cloud Gateway

**Spring Cloud Gateway** 基于 **Spring WebFlux、Reactor 与 Netty**，通过 **`Route`（路由）、`Predicate`（谓词）、`Filter`（过滤器）** 将客户端 **HTTP** 请求映射到下游 **`URI`**[2]。在本课题中，**Gateway** 承担三类与业务代码解耦的工作：一是将 **`/api/**`** 按路径转发到 **user-service（9001）、resource-service（9002）、booking-service（9003）**；二是集中配置 **`globalcors`**，把**浏览器的跨域**处理尽量收在入口，避免各业务服务重复声明 **CORS** 导致响应头叠加；三是为将来在过滤器链上接入 **JWT 校验、限流** 等横切逻辑预留位置。需特别注意：**网关与 `WebMvc` 业务服务若同时开启 CORS**，可能出现 **`Access-Control-Allow-Origin`** 重复、前端 **`Failed to fetch`** 而 **HTTP 状态码仍为 200** 的现象，联调时应以响应头与网关日志为准排查。

#### 2.3.4 OpenFeign 与服务间 REST

**OpenFeign** 在 **Spring Cloud** 中以 **`@FeignClient` 接口 + 方法注解**声明远程 **HTTP**，由框架在运行时生成调用代理并完成序列化与错误传播[3]，比分散的 **`RestTemplate`** 拼装更易维护。本课题中 **resource-service** 通过 **Feign** 访问 **booking-service** 的内部接口 **`GET /internal/bookings/conflicting-resource-ids`**，以 **JSON** 传递 **`date、startTime、endTime`** 并取回冲突资源 **ID** 列表；该路径默认直连 **`http://127.0.0.1:9003`**，**不经 Gateway**，与「浏览器只访问 **9000**」的外网拓扑区分，避免把内部接口误挂到公网路由上。

**前端与持久层**：**Vue 3 + Vite + Ant Design Vue** 负责 **SPA** 与 **`VITE_API_BASE`** 构建注入；**MyBatis-Plus** 在 **MyBatis** 之上提供 **`LambdaQueryWrapper`** 等增强[8]，映射 **`auth_user`、`sys_resource`、`sys_booking`** 等表。二者分别支撑第 5 章前后端实现，本章不再单列展开。

### 2.4 Redis 与分布式锁（Redis and Distributed Locks）

预约提交属于典型的**读—判—写**热点路径：同一时段、同一资源可能被多名用户同时提交，若仅靠数据库本地锁或乐观锁，在工程上往往需要与**缓存层互斥**配合以控制冲突窗口与失败体验。本课题选用 **Redis** 作为内存型中间件，并在 **Java** 侧通过 **Redisson** 使用分布式锁语义。

#### 2.4.1 Redis 的定位与基本特征

**Redis** 以键值结构为主，支持多种数据类型与过期时间，常用作缓存、会话存储与简单计数；其单线程执行命令的模型使**互斥原语**在工程上易于推理[7]。在互斥场景中，常用 **`SET key value NX PX ttl`** 等命令实现「仅当键不存在时写入并带过期时间」，从而避免死锁长期占用。本课题除锁以外，亦可按需扩展缓存用途；当前实现以**预约链路的并发控制**为主。

#### 2.4.2 分布式锁与 Redisson

在分布式环境下，锁状态需要在各实例间可见，**Redis** 常作为协调存储。**Redisson** 在 **Java** 侧封装了 **`RLock`、`tryLock`、leaseTime、watchdog（看门狗）续期**等语义[5]，便于在 **Spring** 的 **Service** 中以接近本地锁的书写方式表达「尝试获取—业务处理—释放」；本课题在 **booking-service** 的预约提交实现中，在写 **`sys_booking`** 前获取锁、失败时返回可理解的业务提示，以缓解同一时刻多次点击提交造成的竞争。与把复杂并发逻辑散落在 **Controller** 相比，把锁嵌在领域服务层更有利于测试与维护。

### 2.5 本章小结（Chapter Summary）

本章在 **2.1** 交代开发环境的基础上，按「**单体与微服务 → Spring Cloud 与网关、Feign → Redis 与 Redisson**」三条主线组织相关技术：既说明了本课题为何保留 **demospringboot** 作对照，也说明了 **Gateway** 与 **Feign** 在拓扑上的不同职责及 **CORS** 配置注意点，并概括了 **Redis** 在预约并发控制中的作用；**Vue、MyBatis-Plus** 作为前后端与持久层的支撑技术，将在第 5 章结合具体页面与表映射进一步体现。

**Spring Boot 3** 以 **Java 17** 为基线，包名迁移至 **Jakarta**，并与 **Spring Framework 6** 对齐，依赖管理与可观测性相关能力较旧版本更为顺手[1]；官方文档亦涉及 **AOT、native hints** 等偏云原生的编译路径。本课题未实际启用 **GraalVM Native Image**，但采用 **Boot 3** 与多模块划分，可与后续镜像化部署、可观测性增强等工作衔接。

### 2.4 Spring Cloud 2023 线路与组件边界

**Spring Cloud 2023.x** 与 **Spring Boot 3.3.x** 的 BOM 对齐后，版本组合冲突会明显减少；本课题实施阶段未将 **Nacos、Sentinel** 等组件全部接入，是有意收窄范围，先把与**网关入口、Feign 调用**强相关的 **starter** 用熟，注册中心与配置中心放在第 7 章展望中说明。

### 2.5 Spring Cloud Gateway：路由谓词、过滤器链与 WebFlux

**Gateway** 借助 **`Route`、`Predicate`、`Filter`** 将入站 **HTTP** 请求映射到下游 **`URI`**，底层基于 **Reactor + Netty**，适合承担**路由、鉴权、限流、CORS**等横切能力[2]；需避免**网关与业务服务重复配置 CORS**，否则响应头中 **`Access-Control-Allow-Origin`** 可能被重复追加，前端仍可能报 **`Failed to fetch`**，而 **HTTP 状态码**却可能为 **200**。

### 2.6 OpenFeign 与契约驱动的服务间调用

**OpenFeign** 以 **`@FeignClient` 与接口方法声明**为核心，由运行时代理完成 **HTTP** 拼装与序列化[3]，相较在各处手写 **`RestTemplate`** 更为整洁；本课题中 **resource-service** 调用 **booking-service** 的 **`/internal/bookings/conflicting-resource-ids`**，即采用该方式。

### 2.7 Redis 与 Redisson 锁语义

**Redis** 中常用 **`SET … NX … PX …`** 一类写法实现互斥；**Redisson** 在 **Java** 侧封装了 **`RLock`、`tryLock`、watchdog** 等语义[5]，嵌入 **Spring** 的 **Service** 后，在预约提交等热点链路上表达清晰。

### 2.8 Vue 3、Vite 与 MyBatis-Plus

**Vue 3** 的 **Composition API** 较 **Options API** 更利于抽取与复用界面逻辑；**Vite** 开发态冷启动较快，配合 **`import.meta.env.VITE_*`** 使用，在构建时将 **`VITE_API_BASE`** 写入产物。**MyBatis-Plus** 在 **MyBatis** 之上提供 **`LambdaQueryWrapper`**、分页插件等能力[8]；本课题中 **`auth_user`、`sys_resource`、`sys_booking`** 等表的持久层映射均依托其实现。

## 第 3 章　系统需求分析

### 3.1 可行性分析（Feasibility Analysis）

（1）**经济可行性**：主要技术栈为开源框架与 **MySQL、Redis**，可在普通 **PC** 或云主机上演示，硬件与软件采购压力小。  

（2）**技术可行性**：**Spring** 生态资料完备[1][12]；微服务与网关模式可参考专著与案例[10][11]；本课题 **platform** 工程已可运行并与 **demospringboot** 对照。  

（3）**操作可行性**：师生通过浏览器完成预约与查询；部署时 **Nginx** 反代 **`/api/`** 至网关即可，使用门槛较低。

### 3.2 功能性需求分析（Functional Requirements Analysis）

系统从业务上可归纳为**用户、资源、预约与审批**三条主线，外加**跨服务可用资源查询**一条协作线：

（1）**用户与认证**：注册、登录、改密；管理员对用户列表、增删、模板下载与 **Excel** 导入导出等维护能力；由 **user-service** 承担。  

（2）**资源管理**：后台对资源的增删改、启用停用；前台按日期与时段查询**可用资源**；由 **resource-service** 承担。  

（3）**预约与审批**：提交预约、我的列表、取消；审批列表中通过或驳回；由 **booking-service** 承担。  

（4）**跨服务查询**：可用资源列表须排除与已有预约冲突的资源，由 **OpenFeign** 调 **booking-service** 内部接口完成，**resource-service** 不作猜测性过滤。  

未单独实现「组织」「统计预测」等扩展模块，可由角色字段与后续迭代覆盖。

### 3.3 非功能性需求分析（Non-Functional Requirements Analysis）

**性能**：多用户同时提交预约时，应避免数据库写入与业务状态出现不一致；**可用性**：服务异常时能在日志中定位，并可通过 **Actuator health** 做健康检查；**安全**：生产环境口令不宜写入版本库，**`/internal/...`** 等内部路径不应暴露在公网网关路由上；**可维护性**：前后端分离、服务边界清晰后，流程变更时能对应到具体 **jar** 模块。

### 3.4 本章小结（Chapter Summary）

本章界定可行性、功能与非功能需求及服务边界。

## 第 4 章　系统概要设计

### 4.1 总体架构设计（Overall Architecture）

从分层与部署视角，系统可描述为：浏览器中的 **Vue SPA** → **Spring Cloud Gateway** → **user-service / resource-service / booking-service** → **MySQL**；预约链路旁挂 **Redis**。本科毕设阶段常将上述组件部署于同一台主机，通过 **`127.0.0.1`** 互通即可满足联调。**架构图源文件**建议使用 `docs/thesis/diagrams/01-system-architecture.md` 导出插入正文。

### 4.2 软件架构设计（Software Architecture）

**端口与职责**：**9001** 用户与认证；**9002** 资源及 **`/api/resource`** 等聚合查询；**9003** 预约、审批、**内部冲突查询接口**及 **Redis/Redisson**；**9000** 网关统一接收 **`/api/**`** 并处理 **CORS**。浏览器与前端 **`VITE_API_BASE`** 仅面向 **9000**，为后续在网关层统一接入 **JWT** 等机制预留位置。

**网关路由（摘要）**：**`/api/login`、`/api/register`、`/api/changePassword`** 与 **`/api/admin/user/**`** → **user-service**；**`/api/resource`** 与 **`/api/admin/list|add|disable|enable`** → **resource-service**；**`/api/booking/**`** 与 **`/api/approval/**`** → **booking-service**；完整路由表见 **`docs/thesis/API.md`**。**`globalcors`** 仅配置在网关，避免与业务服务 **`WebMvc`** 级 **CORS** 叠加。

### 4.3 数据库概要设计（Database Outline）

核心逻辑实体包括**用户、资源、预约**等，主要数据表包括 **`auth_user`**，扩展表 **`auth_student` / `auth_teacher` / `auth_manager`**，**`sys_resource`**，**`sys_booking`**，以及 **`booking_cleanup`** 等辅助表；**`sys_booking`** 与 **`sys_resource`、`auth_user`** 存在外键语义上的关联。**ER 图源文件**建议使用 `docs/thesis/diagrams/06-er-core-tables.md`。

### 4.4 本章小结（Chapter Summary）

本章给出总体拓扑、端口职责、路由摘要与核心表概要。

## 第 5 章　系统详细设计与实现

### 5.1 内部接口与 Feign 设计

**resource-service** 通过 **`BookingFeignClient`** 访问 **`GET /internal/bookings/conflicting-resource-ids`**，查询参数为 **`date`、`startTime`、`endTime`**（**ISO-8601** 字符串），响应为 **`List<String>`** 冲突资源 **ID**；**`booking.service.url`** 默认 **`http://127.0.0.1:9003`**，**不经网关**。**时序图源文件**建议使用 `docs/thesis/diagrams/05-sequence-resource-feign.md`。

### 5.2 关键业务流程

**登录**：**POST `/api/login`** → **Gateway** → **user-service** → **MySQL** 校验用户名、密码与角色，返回 **JSON**（参见 `03-sequence-login.md`）。**预约提交**：**POST `/api/booking/add`** → **booking-service** → **`tryLock`** → 写 **`sys_booking`** → **`unlock`**；失败分支返回可理解的业务提示（参见 `04-sequence-booking-submit.md`）。

### 5.3 网关与全局配置实现要点

**gateway-service** 在 **`application.yml`** 中配置 **`spring.cloud.gateway.routes`** 与 **`globalcors`**，与第 4 章路由设计一致。

### 5.4 各业务服务关键类

**user-service**：**`AuthController`** 提供认证与管理员用户接口。**resource-service**：**`ResourceController`**；**`BookingFeignClient`**。**booking-service**：**`BookingController`、`ApprovalController`、`BookingInternalController`**；**Redisson** 锁嵌入预约服务实现类。

### 5.5 前端实现要点

**`src/config/api.js`**（或等价配置）统一 **`apiUrl`**，与 **`VITE_API_BASE`** 配合，使构建产物指向网关根地址。

### 5.6 非功能性需求在工程中的落实

**健康检查**：各服务可暴露 **Actuator** 端点便于运维查看；**配置分层**：云部署时宜使用 **`spring.profiles.active=prod`** 并将敏感配置移出版本库；**内部接口保护**：**`/internal/...`** 不应出现在对外网关路由表中。

### 5.7 构建与部署实现概述

**`mvn clean package -DskipTests`** 生成各服务 **jar**；建议启动顺序 **user → booking → resource → gateway**；**`npm run build`** 时设置 **`VITE_API_BASE`** 指向 **`https://域名`**；**Nginx** 托管 **`dist`** 并将 **`/api/`** 反代至 **`127.0.0.1:9000`**；细节见 **`docs/thesis/DEPLOYMENT.md`** 与 **`nginx.example.conf`**。**部署拓扑图源文件**建议使用 `02-deployment-topology.md`。

### 5.8 本章小结（Chapter Summary）

本章对应工程中的 **Feign**、主流程、网关配置、关键类与部署要点。
